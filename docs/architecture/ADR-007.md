# ADR-007: The client must send the content type

Status: Accepted

Date: 2026-10-29

## Context

The server delivers each file with a `Content-Type` header.
A browser uses this header to decide how to show the file.
Content sniffing can guess a wrong type. A wrong guess can turn a text file into active HTML.
The uploader knows the type of the file better than the server.

## Decision

- The client MUST send a `Content-Type` header with each upload.
- The server never infers the media type from the filename.
- The server never sniffs the body.
- A missing header gives status 415 with the error code `missing_content_type`.
- A syntactically invalid media type also gives status 415 with `missing_content_type`.
- The server stores the content type and returns it unchanged on GET.
- The client CLI maps common file extensions to a media type.
- For an unknown extension, the client CLI requires the option `--type`.
- The user controls the client. The server stays strict.

## Consequences

Positive:

- The server behavior is simple and predictable.
- The stored type is the type that the uploader declared.
- No sniffing library is necessary.

Negative:

- Raw HTTP clients (for example `curl`) must set the header explicitly.
- The client CLI needs a small extension table. The table needs maintenance.
- An uploader can declare a wrong type. [ADR-010](ADR-010.md) limits the risk of active content.

## Alternatives considered

- Infer the type from the filename extension on the server: hides client errors. Rejected.
- Sniff the body: unpredictable, and a security risk. Rejected.
- Default to `application/octet-stream`: silent and surprising for users. Rejected.
